# MITRE ATT&CK Technique Simulation & Detection Engineering
This lab simulates real attacker behavior on an isolated Azure VM using Atomic Red Team, then build working detections for each teachnique in Microsoft Sentinel -- from raw KQL queries through to live, automated *Analytics Rules* that generate real incidents.

The Mitre Att&ck techniques covered are the following:
| Technique |           Tactic          |                          Detection Logic                              |
|:---------:|:-------------------------:|:---------------------------------------------------------------------:|
| T1110.001 |   Brute Force P.W Guess   |             5+ failed logons from one account in 5 min                |
|   T1018   |  Remote System Discovery  |  2+ distinct recon commands (net/ping/arp) from one account in 5 min  |
| T1059.001 |  Powershell Command Exec  |              PowerShell script block execution events                 | 

**Architecture:**

image

- Windows 10 VM (isolated, single-purpose lab environment
- Log Analytics Wokspace + Microsoft Sentinel
- Two Data Collection Rules:
  - **Windows Security Events via AMA** connector (built-in Sentinel content hub solution) -> feeds the structured 'SecurityEvent' table, configured for ""All Security Events** tier
  - **Custom DCR** with XPath 'Microsoft-Windows-Powershell/Operational*' -> feeds the 'Event' table

Following the Atomic Red Team installment, I explored the library to search for available attack techniques. I selected T1110.001, T1018, and T1059.001. Lets go through each one of them.

**T1110.001 - Brute Force password Guessing (Credencial Access)**

Executed through the VMs powershell the test:

t1110 run image

After this, I went forward to the VMs internal security logs to confirm that logs were indeed generated by this attack simulation. This was positive, so I went back to the Azure Log Anaytics Workspace to up set the KQL detection query by using parameters such as EventID 4625, count function of FailedAttempts, and setting up the treshold. This KQL detection query was succesfull, concluding that the logs were properly being streamlined to Azure without any false-positives since the given treshold is anomaly-based (FailedAttempts >= 5 in under 5 min).

**T1018 - Remote System Discovery**

Executed through the VMs powershell the test:

The test by itself was properly ran by the Atomic Red Team test workflow. However, reconnaissance wasn't succesful due to the nature of the VM itself. The VM is isolated on its own virtual network with no other machines to discover. So I decided to make the reconnaissance myself via a loopback (127.0.0.1 localhost) for the sake of this lab.

This succesfully generated the security logs, so I went back to Azure to setup the KQL detection query by using parameters such as EventID 4688, process search (net.exe, ping.exe, arp.exe) and setting up the treshold. This KQL detection query was succesful, ensuring proper stream of logs to Azure.

**Lessons Learned**

- *Detection logic needs to match what a technique **actually** generates — I set up my discovery query to require 2+ distinct commands as treshold to avoid false-positives, but the atomic test alone only produced one; 
  had to manually extend the simulated behavior to properly exercise the detection.*

- *Not every documented ATT&CK technique has platform-appropriate tooling available — 
  validating tool/OS compatibility before committing to a technique saved significant rework.*
  
- *Alert grouping settings matter operationally: without "group all alerts from this rule into 
  a single incident", a single real brute-force testing generated over 300 duplicate 
  incidents in a matter of hours — a good reminder of how incident fatigue happens in real 
  SOC environments.*
